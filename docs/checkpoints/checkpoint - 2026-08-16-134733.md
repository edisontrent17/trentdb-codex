# Checkpoint - 2026-08-16 13:47:33 UTC

## Goal

Define the long-term target and a test-driven way to execute it without treating the DuckDB rewrite as one unbounded task.

The active project goal is to rewrite DuckDB core in Java while preserving DuckDB-shaped subsystem boundaries and DuckDB-compatible behavior. The chosen external acceptance corpus is DuckDB's upstream SQLLogic test suite. The upstream `.test` files should be consumed directly rather than rewritten as Java test cases.

No earlier checkpoint was produced in the visible conversation. The repository contains an older historical checkpoint from April 2026, but this document records the decisions, measurements, and verification performed during the current project-status and goal-definition session.

## Architecture

The existing Java implementation already follows this pipeline:

`SQL -> AST -> binder -> logical plan -> optimizer -> physical plan -> vectorized execution`

The repository has explicit packages for parser/AST, catalog, types, binder/planner, optimizer, physical execution, functions, storage, and transactions. This is structurally aligned with the intended DuckDB architecture.

The implementation is currently strongest on read-only analytical execution. The largest missing production subsystems are:

- an engine/connection facade that can execute arbitrary SQL statements while retaining session state
- end-to-end `CREATE TABLE` and `INSERT` execution
- a transactional write path coordinating catalog and table changes
- write-ahead logging, commit records, flush ordering, recovery, and checkpoints
- real MVCC visibility for catalog entries and rows
- parallel scheduling and concurrent execution
- primitive-specialized vectors and production storage internals
- the broad SQL, type, function, DDL, DML, and extension behavior exercised by DuckDB's SQLLogic suite

## Interfaces

No production interfaces were added or changed in this checkpoint.

The analysis identified the future test-facing boundary that will be required:

- a persistent database/session object rather than a one-query helper
- an `execute(sql)` operation capable of returning either a materialized result or a structured error
- database restart and reconnection hooks for persistence tests
- named or multiple connections for concurrency tests
- stable value/type rendering compatible with DuckDB SQLLogic expectations

The SQLLogic harness itself will need representations for:

- `statement` expectations (`ok`, `error`, `maybe`, or equivalent upstream modes)
- `query` expectations, type signatures, sort modes, labels, literal results, result hashes, and file-backed expectations
- `skipif` and `onlyif` conditions
- `loop`, `foreach`, `concurrentloop`, `concurrentforeach`, `continue`, and `endloop`
- `load`, `restart`, `reconnect`, `include`, `unzip`, and `sleep`
- `require`, `require-env`, `test-env`, `tags`, `set`, `reset`, `mode`, `hash-threshold`, and `halt`

Unsupported harness directives must fail explicitly. They must not silently skip an upstream test.

## Flow

The intended compatibility flow is:

`Pinned DuckDB checkout -> unchanged .test file -> SQLLogic parser -> directive executor -> Java database/session -> result normalizer -> upstream expectation comparator -> parity report`

The default Maven suite remains the fast repository health gate. The upstream SQLLogic run is a separate cumulative compatibility gate because it is much larger, requires the DuckDB checkout and fixtures, and initially contains many legitimate failures.

The compatibility report must distinguish at least:

- `PASS`: the unchanged upstream test passed
- `ENGINE_FAILURE`: the runner worked and exposed missing or incorrect database behavior
- `RUNNER_UNSUPPORTED`: the SQLLogic language or harness behavior is not implemented yet
- `ENVIRONMENT_BLOCKED`: an upstream-declared dependency is unavailable
- `HARNESS_ERROR`: malformed runner state or an infrastructure defect

No TrentDB-specific skip category should exist. Environment blocking should follow upstream DuckDB predicates and remain visible in totals.

## Behavior

The current Java engine supports a substantial read-only SQL subset, including:

- catalog and CSV replacement scans
- projections, aliases, filters, arithmetic, null-aware boolean logic, casts, dates, and intervals
- grouped and ungrouped aggregates, distinct aggregate arguments, and `HAVING`
- inner and left joins
- derived tables and non-recursive CTEs
- supported scalar, `IN`, `EXISTS`, and correlated scalar aggregate subquery shapes
- ordering, limits, and logical/physical `EXPLAIN`
- optimizer rewrites including expression simplification, projection pruning, and filter pushdown

`CREATE TABLE` and `INSERT` are parsed, but they are not bound, logically planned, or executed through the general query path. Therefore the inspected upstream arithmetic SQLLogic file fails at its first setup statement against the current engine. This is an engine gap, not a reason to skip the test.

## Checkpoint Strategy

Each implementation checkpoint should satisfy the following invariant:

1. Pin the exact DuckDB commit and record it.
2. Name the upstream test shard or capability gate targeted by the checkpoint.
3. Record the baseline counts by failure category before implementation.
4. Implement one end-to-end DuckDB-shaped slice.
5. Run the full Maven suite.
6. Run every previously passing SQLLogic file plus the new target shard.
7. Record new pass/failure totals and prevent pass-to-fail regressions.
8. Save a checkpoint document with architecture, files, behavior, tests, limitations, and next steps.

Recommended cumulative checkpoints:

### C0 - Contract and Inventory

- pin the upstream revision
- inventory every `.test` file and required fixture
- define pass, failure, environment-blocked, and harness-error semantics
- produce the initial zero-pass/full-corpus manifest

### C1 - SQLLogic Harness

- parse every upstream test file without silently ignoring directives
- implement statement/query expectations and result normalization
- implement selection by file, directory, tag, and manifest shard
- produce deterministic machine-readable and human-readable reports

Exit criterion: every upstream file is discoverable and classified; parser/runner limitations are explicit.

### C2 - Database Session and Foundational Writes

- introduce a persistent database/session execution facade
- execute `CREATE TABLE`, `INSERT`, and `SELECT` through catalog, storage, and transaction boundaries
- avoid direct parser/binder/planner mutation of catalog or storage

Exit criterion: the first unchanged upstream setup/query files pass cumulatively.

### C3 - Core Types and Expressions

- numeric and text types, null semantics, casts, comparisons, arithmetic, scalar functions, overflow, and error behavior
- exact SQLLogic value rendering and type signatures

### C4 - Relational Query Core

- joins, aggregates, grouping sets as encountered, set operations, subqueries, CTEs, ordering, limits, and window functions

### C5 - Catalog, DDL, and DML

- schemas, views, sequences, constraints, alter/drop behavior, update/delete/merge, prepared statements, and catalog errors

### C6 - Durable Storage and Lifecycle

- on-disk database format strategy
- WAL ordering, commits, rollback, checkpoints, restart/reconnect/load, recovery, and corruption behavior

### C7 - MVCC and Concurrency

- snapshot visibility, atomic catalog/data commits, multiple connections, conflict rules, concurrent loops, cleanup, and isolation

### C8 - Optimizer and Execution Depth

- broad optimizer parity, statistics, join ordering, pushdowns, memory behavior, spilling, parallel pipelines, and plan-sensitive behavior

### C9 - Advanced Types, Functions, and Extension-Backed SQLLogic

- lists, structs, maps, unions/variants, decimals, temporal breadth, collations, JSON, Parquet, ICU, and other behavior required by the selected upstream SQLLogic corpus

This checkpoint acknowledges that selecting every upstream SQLLogic file expands the practical behavior target beyond a narrow definition of DuckDB core.

### C10 - Full Pinned-Corpus Closure

- zero engine failures
- zero runner-unsupported files
- zero harness errors
- only upstream-authorized environment conditions may remain blocked
- complete Maven suite remains green

After C10, advance the DuckDB pin and repeat through delta checkpoints rather than treating upstream movement as an unbounded rewrite.

## Limitations

- The checkpoint plan is not evidence of compatibility; no SQLLogic runner has been implemented yet.
- Raw file counts do not measure semantic complexity or percent completion.
- The local DuckDB test corpus changes with its pinned revision; the pin must be explicit for reproducible claims.
- Full SQLLogic parity includes extension-backed and environment-sensitive behavior even though the original project goal was phrased as a core rewrite.
- The Java implementation currently has in-memory storage and snapshot-shaped transaction placeholders, not production durability or isolation.
